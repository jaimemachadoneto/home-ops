# Semaphore (Raspberry Pi 3B)

Ansible Semaphore running as a standalone Docker container on a Raspberry Pi
3B (`semaphore.local.jaimenet.com`, static LAN IP `10.30.50.210`), outside
the Kubernetes cluster. Reachable at `https://semaphore.${SECRET_DOMAIN}` via
the cluster's `envoy-internal` gateway (see
`kubernetes/apps/external-ingresses/semaphore/`), which routes to the Pi
through an Envoy Gateway `Backend` with an `fqdn` endpoint (NOT a Kubernetes
`Service`/`Endpoints` - Envoy Gateway doesn't support `type: ExternalName`
Services as HTTPRoute backends, it silently 500s).

## Layout

- `docker-compose.yml` - the Semaphore stack. Pinned image tag+digest so
  Renovate can open version-bump PRs.
- `semaphore.env.example` - template for the two secrets (admin password,
  access key encryption key). The real file lives only on the Pi at
  `/opt/semaphore/semaphore.env`, generated by `install.sh`, never committed.
- `install.sh` - one-time host bootstrap: Docker Engine, app directories,
  secrets, NAS backup mount + timer, and doco-cd itself.
- `scripts/backup.sh` - tars the SQLite DB + config to the NAS.
- `systemd/semaphore-backup.{service,timer}` - daily backup timer.
- `doco-cd/` - the GitOps deployer that actually runs and updates the
  Semaphore container (see below).
- `../.doco-cd.semaphore.yml` (repo root) - doco-cd's deploy config for this
  stack. Must live at the repo root; doco-cd only auto-discovers nested
  `.doco-cd.yml` files, not target-named ones.

## Why doco-cd instead of Flux

The Pi isn't part of the Kubernetes cluster, so Flux can't reconcile it.
[doco-cd](https://doco.cd) is a small Go tool built for exactly this: it
polls a git repo and runs `docker compose up` when the relevant path
changes - a GitOps loop for a single bare Docker host. It runs as its own
container on the Pi (`/opt/doco-cd`), polls `home-ops` every 5 minutes over
SSH (read-only deploy key), and deploys `hosts/semaphore/docker-compose.yml`
whenever it or `.doco-cd.semaphore.yml` changes on `main`.

Renovate already opens PRs bumping the pinned image tag in
`docker-compose.yml` (same as the k8s apps in this repo) - merge one and
doco-cd redeploys it within 5 minutes. No manual SSH needed for routine
updates.

## Fresh install / reinstall

```sh
ssh jaime@semaphore.local.jaimenet.com
git clone --depth 1 git@github.com:jaimemachadoneto/home-ops.git /tmp/home-ops
cd /tmp/home-ops/hosts/semaphore
./install.sh
```

`install.sh` will print a public key partway through - add it as a
**read-only** deploy key on the repo (link is printed) before doco-cd can
pull. Everything is idempotent, so re-running after a fresh SD card flash
(or to pick up script changes) is safe.

Once the deploy key is registered, doco-cd takes it from there - it deploys
the Semaphore container itself within one poll interval. Watch it with:

```sh
docker logs -f doco-cd
```

## Credentials

- Admin login: `admin` / see `/opt/semaphore/semaphore.env` on the Pi
  (`SEMAPHORE_ADMIN_PASSWORD`, mode 600, owned by `jaime` - NOT the
  container's uid 1001, since only the host-side `docker compose` needs to
  read it).
- `SEMAPHORE_ACCESS_KEY_ENCRYPTION` in the same file encrypts the Ansible
  access keys/secrets stored inside Semaphore's own DB - back it up, losing
  it makes those unrecoverable even if you still have the DB file.
- doco-cd's deploy key: `/opt/doco-cd/deploy_key` (private, read-only on
  GitHub, not committed anywhere).

## Backups

`scripts/backup.sh` tars `/opt/semaphore/{data,config,semaphore.env}`
(SQLite DB + config.json + secrets) nightly via `semaphore-backup.timer`,
keeping 2 days locally in `/opt/semaphore/backups` and 14 days at
`nas.jaimenet.com:/mnt/Data1/semaphore` (mounted at `/mnt/semaphore-backup`
via `x-systemd.automount`, so a NAS outage doesn't block boot or block the
timer - it just falls back to local-only for that run).

The NAS export is normally read-only for arbitrary LAN clients; the Pi's IP
(`10.30.50.210`) needs an explicit read-write ACL entry for
`/mnt/Data1/semaphore` on the NAS admin UI, same as it's presumably granted
for the k8s node IPs already backing up to `/mnt/Data1/kubernetes`.

### Restore

```sh
ssh jaime@semaphore.local.jaimenet.com
cd /opt/doco-cd && docker compose down   # stop doco-cd so it doesn't fight the restore
cd /opt/semaphore && docker compose down
tar -xzf /mnt/semaphore-backup/semaphore-<timestamp>.tar.gz -C /opt/semaphore
sudo chown -R 1001:1001 /opt/semaphore/data /opt/semaphore/config
cd /opt/semaphore && docker compose up -d
cd /opt/doco-cd && docker compose up -d
```

## Known gotchas (learned the hard way)

- This Semaphore version (v2.19+) **dropped BoltDB support** - the
  interactive setup menu still lists it but tags it "NOT SUPPORTED" and the
  server panics on `SEMAPHORE_DB_DIALECT=bolt`. Use `sqlite` (the default;
  reuses `SEMAPHORE_DB_HOST` as the file path).
- The container runs as uid 1001. Any host directory bind-mounted for it to
  write into (`/var/lib/semaphore`, `/etc/semaphore`, `/tmp/semaphore`) must
  be `chown 1001:1001`, not owned by the SSH user.
- `semaphore.env` must NOT live inside a directory owned by uid 1001 - if it
  does, the host-side `docker compose` (running as the SSH user) can't read
  it to populate `env_file`, and secrets silently come up empty.
- doco-cd resolves `env_file:` paths itself, client-side, before talking to
  the Docker daemon over the mounted socket - so absolute host paths
  referenced in `docker-compose.yml` (like `/opt/semaphore/semaphore.env`)
  must also exist at that *same path* inside doco-cd's own container, not
  just on the host. Hence the `/opt/semaphore:/opt/semaphore:ro` mount in
  `doco-cd/docker-compose.yml`.
- doco-cd does NOT run with `cap_drop: ALL`, on purpose: without
  `CAP_DAC_OVERRIDE` it can't read files it doesn't own (the deploy key,
  `semaphore.env`), and loosening those files' permissions instead would
  expose real secrets. Dropping caps buys little here anyway - the mounted
  `docker.sock` is already root-equivalent on the host.
